# Benchmarks

## Reproduce

```
pip install .
python bench/run_bench.py            # writes results/bench.json and results/bench.md
python tools/summarize.py            # writes results/summary.md from every results/bench*.json
```

`--quick` runs five small cases in about a minute. On Windows the script restricts itself to logical CPUs 0-13 by default (`--cpus all` turns that off); see [Noise](#noise-on-this-machine).

## What is measured

- **Operation:** build a packer with `newPacker()` defaults (offline mode, best-bin-fit, `MaxRectsBssf`, sort by area, rotation on), add all rectangles and bins, call `pack()`, read `rect_list()`. The whole call is timed, including Python-side setup.
- **Three variants, same inputs:**
  1. `original`: rectpack 0.2.2, untouched.
  2. `python_fixes`: the original with two pure-Python changes and no C++ (`bench/cheap_wins.py`).
  3. `native`: fastrectpack.
- **Workloads** (`bench/workloads.py`, fixed seeds, integer sizes):
  - `random`: sides uniform in 10-100, bins 1000x1000.
  - `cutting`: 20 typical sheet-part sizes with heavy repetition, bins 2440x1220. Uses many bins.
  - `sprites`: sides drawn from 16 to 256 in the usual texture steps, bins 2048x2048.
  - `skewed`: 5% large pieces (200-600), the rest small (5-60), bins 1500x1500.
- **Procedure:** the variants are run interleaved in rotating order, so background load affects them alike. One warm-up round for cases up to 1,000 rectangles. Rounds: 7 up to 1,000 rectangles, 5 at 2,000, 3 at 5,000. Garbage is collected before each timed call.
- **Statistic:** best (minimum) time per variant, and speedup = best original time / best variant time. Background load only ever adds time, so the minimum is the closest estimate of the code's own cost. The table also shows the range of per-round speedups from the main run.
- **Parity:** each run hashes the full output of all three variants. A mismatch fails the script.

## Float and numpy sizes (0.2.0)

`python bench/run_mixed.py` writes `results/mixed.json` and `results/mixed.md`. Measured 2026-11-10 on the same machine, numpy 2.5.4.

- **Settings:** offline mode, best-bin-fit, `MaxRectsBlsf`, sort by area, rotation off, one bin with sides `sqrt(2.2 * total area / 2)`, so everything fits. These are the settings in `gdsfactory/pack.py`.
- **Inputs:** rectangle sides are integers uniform in 10-200. "gdsfactory" passes them as `int` with a `numpy.float64` bin. "float" adds 0.25 and 0.1 to the sides and passes Python floats everywhere. "numpy.int64" reads the sides from an int64 array and uses an `int` bin.
- **Procedure:** original and fastrectpack interleaved, 7 rounds with one warm-up up to 300 rectangles, 3 rounds without warm-up at 1,000. Speedup is best original time over best fastrectpack time.
- **Parity:** the digest covers the type of every number in `rect_list()` as well as its value.

The ratios are higher than in the table above for two reasons that have nothing to do with floats: all rectangles go into one bin, so the free list is longer and the original's all-pairs comparison costs more, and the Python bin-selection loop has only one bin to ask. An all-`int` run of the same single-bin job gave a similar ratio to the gdsfactory case in an informal check (one timing of the original).

**gdsfactory's own function.** `_pack_single_bin` was copied unmodified from `gdsfactory/pack.py` and run with `rectpack` and then with `fastrectpack` standing in for it, on sizes built the way `gdsfactory.pack` builds them. Results were identical in value and type. Timed once each: 0.015 s against 0.0013 s (50 rectangles, 12x), 0.370 s against 0.0046 s (200, 81x), 5.188 s against 0.0155 s (500, 335x). gdsfactory itself was not installed or run.

**The fallback is not slower than rectpack.** 0.1.0's notes said it was, by about 2x. `research/fallback_slowdown.py` shows the fallback makes 8,875,000 Python function calls where rectpack makes 8,874,390, and takes the same time in every interleaved round. The earlier figures compared two timings taken one after the other on this machine; see `results/fallback_slowdown.txt`.

## Where the time went in the original

`bench/profile_original.py` (cProfile, so read the shares, not the seconds):

| Function | random, 1,000 | skewed, 1,000 |
|---|---|---|
| `_remove_duplicates` | 93.7% | 88.2% |
| `_select_position` | 3.6% | 7.6% |
| `_split` | 2.4% | 3.7% |

After every placement, `_remove_duplicates` compares every pair of free rectangles: 30.8 million `contains()` calls to place 1,000 rectangles in the random case, with a mean of 146.5 free rectangles per search.

## Where the speedup comes from

1. **Incremental duplicate removal (pure Python).** The free list never holds a rectangle that contains another once the step has run, so only pairs involving newly created pieces need checking. Measured alone: 1.0x to 7.1x (`results/phase3.json`).
2. **Single fitness evaluation (pure Python).** The original computes each candidate's fitness twice. Together with step 1: 1.7x to 7.5x.
3. **C++ port.** The same algorithm on plain structs instead of Python objects.

## Noise on this machine

- **Hybrid CPU.** The same fixed loop takes 378-414 ms on logical CPUs 0-13 and 577-1,501 ms on CPUs 14-27 (`bench/probe_cores.py`). An unrestricted process drifts between them: the first baseline showed identical runs taking 21 s and 57 s. The benchmark therefore restricts itself to CPUs 0-13.
- **Slow phases.** Even on the fast cores, the machine drops into stretches where everything runs about 2.3x slower. Other background software was running during the first two full runs, but the third run, with it closed and the laptop on mains power, showed the same slow phases, so it is not the main cause. Thermal or power throttling is the likely explanation; I did not confirm it. Because variants are interleaved, a slow phase moves all three together: best-time speedup ratios agreed to roughly 10% between full runs, while absolute seconds did not.
- **Consequence.** Treat the speedup ratios as the result. Treat the absolute seconds as approximate. A re-run on a desktop, or a laptop that does not throttle, would firm them up.

Raw files: `results/bench.json` (main run, the third, with other software closed), `results/bench_run2.json` (second run), `results/bench_run1_single_core_pin.json` (first run, pinned to one core), `results/baseline.json` (original only), `results/phase3.json` (pure-Python steps). `results/baseline_unpinned_UNRELIABLE.json` is kept as evidence of the core-drift problem; its best times are included in the "best" columns only because lower original times make the speedup claim more conservative.
